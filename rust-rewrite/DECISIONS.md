# Decisions

Choices the Windows goal made, each with its reason and the alternative left open. `REQUIREMENTS.md` outranks this file; `SWEETVIEW-RESTART-PROPOSAL.md` is the design these adjust.

## D1. The crates and their boundaries

All under `crates/`, all from this repository; every dependency is from crates.io.

| Crate | Job | Why it is its own crate | `unsafe` |
|---|---|---|---|
| `sweetview-runtime` | everything that lives on the UI thread, with no JavaScript in sight: the loop in both modes and the objects on it | so the behaviour is testable with `cargo test`, with closures where JavaScript functions will be | forbidden |
| `sweetview-napi` | the binding: converts JavaScript values and functions and calls the runtime | the only crate that knows both N-API and the runtime; keeps N-API types out of everything else | forbidden |
| `sweetview-platform-node` | the export table: the items that carry `#[napi]`, each forwarding to `sweetview-napi` | see D2 | generated only; none hand-written |
| `sweetview-platform-loop` | the parts of the UI thread's loop `tao` has no API for: the window target while the loop runs, a wake and timers that arrive inside any modal loop; and the three things every other platform crate needs of a thread's loop: a message-only window with a poster, the pump calls, the handle counts | see D3 and D4; the shared pieces live here so each exists once (D23) | yes |
| `sweetview-http` | the rules of the webview's request handler that need no OS call: status and header validation, asset paths, origins, limits, the error codes | pure logic, ported with the C++ library's tests, shared by Windows now and macOS later | forbidden |
| `sweetview-keycodes` | the tables that turn an OS key or mouse message into the values applications see | pure data and decisions for both platforms' hooks | forbidden |
| `sweetview-window-logic` | what a window should do next, decided from cursor positions, button states and bounds: hit regions, the resize gesture, the frameless maximise, the extended-style policy | the state machines are testable without a window | forbidden |
| `sweetview-platform-webview` | what the webview needs on top of `wry` that `wry` has no API for: the request handler with streamed bodies, drops, user scripts, the tab hooks | all of it reaches WebView2 through the typed interfaces `wry` hands out | yes |
| `sweetview-platform-input` | system-wide mouse and keyboard hooks and the permission model | one OS mechanism, unrelated to windows or the webview | yes |
| `sweetview-platform-window` | the window-level OS calls `tao` has no API for, and the events of any window by subclass | see D8 | yes |
| `sweetview-platform-notify` | desktop notifications with a click that comes back | WinRT toasts and the balloon fallback are one feature with its own threads and registrations | yes |
| `sweetview-platform-shell` | the shell integrations that are one OS conversation each: clipboard text, URL schemes, single instance, icon refresh | small, unrelated to the loop; none needs a window of Sweetview's | yes |

## D2. The binding is two crates: `sweetview-napi` and `sweetview-platform-node`

Requirement: the binding forbids `unsafe` (R4, W0.3).

Observed: `#[napi]` on a function or class does not compile under `#![forbid(unsafe_code)]`. `napi-derive` 3.7.2 registers each export through the `ctor` crate, whose expansion carries `#[allow(unsafe_code)]`; the compiler rejects an `allow` under a `forbid`:

```
error[E0453]: allow(unsafe_code) incompatible with previous forbid
  = note: this error originates in the macro `$crate::__ctor_parse_impl` which comes from the expansion of the attribute macro `napi`
```

Decision: everything the binding does lives in `sweetview-napi` as ordinary safe functions under `#![forbid(unsafe_code)]`. The attribute lives in `sweetview-platform-node`, where every item is one forwarding call. That crate is named as a platform crate because the attribute's expansion is `unsafe extern "C"` code; it holds no hand-written `unsafe`, and `verify.ts` reports it with a count of zero.

Alternative left open: register exports by hand through `napi`'s non-macro API. It needs a hand-written `unsafe extern "C"` entry point and loses the generated TypeScript declarations.

## D3. Wakes, deferred jobs and native timeouts go through a message-only window, not `tao`

The proposal has `wake(handle)` send a `tao` user event. `tao` on Windows buffers every event while its handler is running (`EventLoopRunner::send_event`), and its handler is running whenever a handler has opened a modal loop. A worker's reply, a deferred UI method and the ready watchdog must all arrive inside such a modal loop (W1.8).

Decision: `sweetview-platform-loop::SignalWindow` is a message-only window. A wake is a message posted to it; a timeout is a timer on it. Whichever message loop the UI thread is in dispatches both: `tao`'s, a dialog's, a popup menu's, an application's own. This is what `win32/message-window.ts` and `webview_dispatch` do today.

Two consequences found by test:

- `tao` calls its event handler only for its own messages, so `Runtime::request_exit` sends a `tao` user event to make the blocking run look at its exit flag.
- The OS serves a timer message only when nothing else is queued, and a pumped `tao` loop always has its own repaint request queued. `Runtime::pump` therefore takes the signal window's due timers explicitly after each pump (`SignalWindow::dispatch_due_timers`).

Alternative left open: `tao`'s `EventLoopProxy` for wakes and `ControlFlow::WaitUntil` for timeouts, which fails W1.8.

## D4. `LoopHost` keeps a clone of the loop's window target

`tao`'s `run_return` borrows the `EventLoop` mutably for the whole run and gives the window target only to its event handler. A callback that the OS delivers inside the run but outside that handler (a WebView2 handler, a signal, a tray click) still has to be able to create a window, because JavaScript can do so from any callback.

Decision: `LoopHost` takes a clone of the loop's `EventLoopWindowTarget` when the loop is handed to it and lends that through `LoopHost::with_target`, whether or not a run is in progress. `tao` 0.38's target is `Clone`, and a clone shares the loop's thread, message target and runner with the one `tao` passes to the handler. No `unsafe`. (The first form recorded the pointer `tao` passed to the handler and lent it during the run, with one `unsafe` dereference; the safety pass replaced it.)

Alternative left open: route every callback through `tao`'s handler so the target is always at hand; it fails W1.8 for the reason in D3.

## D5. The built binding is not tracked; its declarations are

`packages/sweetview-native/prebuilt/sweetview.<target>.node` is built by `just native` (and by CI) and ignored by git. `packages/sweetview-native/prebuilt/binding.d.ts`, generated from the Rust signatures by the same command, is tracked, so the TypeScript in the repository typechecks against a known surface and a change to the surface shows in review.

Reason: a tracked binary changes on every rebuild and grows the repository with each one. The published package carries the binary through its `files` list (W8.1).

Alternative left open: track the binary, so a clone runs with no Rust toolchain.

## D6. The UI thread is the thread that loads the binding first

`sweetview_runtime::threads` records the first thread to load the binding, which is the Bun main thread. Every UI-thread function checks it and throws `sweetview: this call must be made on the UI thread` elsewhere. `tao` is built with `with_any_thread(true)`, because inside a host process its own idea of the main thread (the thread that ran the library's static initialisers) is the same thread but is enforced with a panic instead of an error.

## D7. A thrown JavaScript exception is logged by the TypeScript wrapper, with the binding as backstop

Each application handler is wrapped in TypeScript before it reaches the binding, and the wrapper logs an exception with the message today's code logs for that handler. `JsCallback::call` in `sweetview-napi` catches whatever still reaches it, logs `sweetview: <kind> threw: <reason>`, and reports `None` to the runtime, which then uses the callback's failure value (a hook does not swallow, a request answers 500).

Reason: today's messages live in the TypeScript layer already, per handler; keeping them there keeps them identical.

## D8. Windows are made by `tao`; their events and the styles `tao` does not model come from one subclass

`tao` creates every window Sweetview owns (frame, DPI awareness, dark title bar, alpha composition, drag, maximise). Two things are not taken from `tao`:

- Events. `tao` delivers `Resized`, `Moved`, `CloseRequested` and `DroppedFile` through its event handler, which it holds back while that handler is already running (a handler with a modal dialog open) and never calls under a message loop `tao` does not run (an application's own `bun:ffi` loop). Today those events arrive synchronously inside any loop. `Window.fromHandle` needs a subclass for a window `tao` did not create in any case, so the same subclass (`SetWindowSubclass`, in `sweetview-platform-window`) is the event source for every window, owned or adopted, with one code path.
- Extended styles `tao` has no flag for. `tao` rewrites the whole extended style from its own flags whenever one of them changes, which would drop `WS_EX_TOOLWINDOW` (off the taskbar and out of Alt+Tab; `tao`'s `set_skip_taskbar` removes the taskbar button only), `WS_EX_LAYERED` for `colorKey` and `opacity`, and the click-through bits while a layered window must stay layered. The subclass answers `WM_STYLECHANGING` with the bits Sweetview wants forced on and off, so they hold whoever changes the style.

Bounds are set with one `SetWindowPos` in the platform crate, because `tao` offers an outer position and an inner size as two calls, and a window dragged by its left or top edge must move and resize in one step.

Alternative left open: `tao`'s `WindowEvent`s and `set_ignore_cursor_events`, re-applying the extra styles after every `tao` call; it changes when events arrive and flickers a layered overlay each time click-through flips.

## D9. A window is shown by the platform crate, and `tao` is told afterwards

`tao`'s `set_visible(true)` shows with `SW_SHOW`, which activates even a `WS_EX_NOACTIVATE` window; `noActivate` windows must never take focus. `show()` therefore runs today's sequence in `sweetview-platform-window` (restore if minimised, `SW_SHOWNOACTIVATE` for `noActivate`, the foreground otherwise), and the subclass keeps `tao`'s later style rewrites from changing `WS_VISIBLE`.

Alternative left open: `tao`'s `set_visible`, which changes focus behaviour for overlays.

## D10. A quit asked for outside a blocking run waits for the next pump

The C++ library ended a loop by posting a quit message, so `quit()` called while no `run()` was in progress ended the next `run()` at once, or made the next `pumpEvents()` return false, and `discardQuit` took it back. The runtime keeps that contract without the message: `Runtime::request_exit` outside a blocking run sets a flag the next pump reports and consumes, the next blocking run ends at once on it, and `discard_quit` clears it (and still takes back a real quit message an application posted).

Alternative left open: make `quit()` a no-op unless a blocking run is in progress; an application that pumps with `runEventLoop` and ends its loop by `app.quit()` would then never stop.

## D11. One pump dispatches everything that is waiting

`tao` in poll mode hands its handler `MainEventsCleared` after each message, so a pump that exits there dispatches one message per call. `pumpEvents` has always dispatched everything waiting. `Runtime::pump` goes round until no posted message waits, bounded at 256 rounds, then takes the signal window's due timers (D3).

## D12. The binding's built-in types are positional where an object would need `unsafe`

`#[napi(object)]` structs compile under `#![forbid(unsafe_code)]` and are used for data that crosses the boundary as an object (`Rect`, `RawRequest`, `KeyData`, `WindowInit`). Callback types are written out in each `#[napi]` signature in `sweetview-platform-node`, because a Rust type alias erases the parameter types from the generated TypeScript declarations.

## D13. Tray events are queued, never run inside `tray-icon`'s window procedure

`tray-icon` reports the shell's mouse messages from the icon's own window procedure, to one handler per process, while it holds its own state borrowed. The runtime's handler only queues the event as a deferred job (D3); the job runs on the next turn of whichever loop the UI thread is in. An application's click handler may therefore dispose of the tray, change its icon, or open a modal loop. The single and double click rule (a left click is a click only once the double-click time has passed with no second click) is safe Rust on a native timeout, as `win32/tray.ts` had it.

Alternative left open: call the application from inside the event handler; a handler that disposes of its tray would then free `tray-icon`'s state under its own borrow.

## D14. Menus are built fresh for each showing; item icons are 16 pixels

A menu crosses the boundary as data each time it is about to open, and a `muda` menu is built for that one showing and dropped after it, so labels, check marks and enabled state follow application state with no bookkeeping and nothing outlives the showing. `muda` draws an item's icon into a 16 by 16 bitmap, so the icon is decoded and resampled to that size by the runtime (`icon.rs`) from the `.ico` or PNG bytes the application gave. An item with both an icon and a check mark, which `muda` has no item type for, gets its check from `sweetview-platform-window::popup::check_item`.

## D15. The WebView2 environment is created the way the C++ library created it, once per process

`wry` creates its environment with browser arguments, a language and the extensions flag. Two environments on one user data folder with different options cannot run at once (`ERROR_BUSY`), so an application running an old build beside a new one, or sharing its profile across an upgrade, would fail to start its webview. `sweetview-platform-webview` creates the environment with no options, on the folder the C++ library used (the roaming application-data folder joined with the executable's file name, or `WEBVIEW2_USER_DATA_FOLDER` when set), keeps one per process, and hands it to `wry` through `with_environment`. An application's profile (cookies, local storage, service workers) is the same folder before and after the upgrade.

Alternative left open: let `wry` create it; existing profiles would then be unusable while any old build runs, and every origin's storage would start empty wherever `wry`'s default folder differs.

## D16. A page message is answered on a later turn, and a webview is dropped after its callback returns

A binding's function runs as a deferred job, not inside WebView2's `WebMessageReceived` callback, so it may open a modal dialog (W1.8) or destroy the webview. `destroy` marks the webview destroyed at once (no handler runs again; late answers get the documented `-3`), and the `wry` value is dropped when no callback of that webview is on the stack. This is the rule the proposal keeps from today ("a webview is never destroyed inside its own callback"), enforced in one place, `sweetview-runtime/src/engine.rs`.

## D17. Dropped files reach the host as one string message

The proposal names the C++ library's method: a script posts the dropped `File` objects with `postMessageWithAdditionalObjects`, and a `WebMessageReceived` handler reads each `ICoreWebView2File`. WebView2 delivers the additional objects only with a string message, which is what the C++ library posts; the platform crate posts the string `__sweetview_file_drop__` with the files attached and tells that message from the page's own by its exact text and its attached objects. `wry`'s drag-drop handler stays unused on Windows, as the proposal says, so drops inside the page still reach the page.

## D18. The macOS seam is one module per shared file, and the bindings package loads only on macOS

`packages/sweetview/src/webview-host.ts` is the seam R8 asks for: on Windows it returns the Rust engine; on macOS it returns today's code, which now lives in `darwin-webview-host.ts`, `darwin-webview-lib.ts` and `darwin-worker-wake.ts`. In the native package, `darwin/library.ts` is the only file that imports `@n1h/sweetview-webview-bun`, with a dynamic `import()` inside a `try` behind a platform test, so a Windows application bundles and compiles without that package installed; it is an optional peer dependency until the macOS goal removes it.

## D19. No list of dependent applications was made by this session

R2 runs the upgrade against each application listed in `rust-rewrite/local/dependents.txt` when that file exists. The file did not exist on this machine. Making one would mean searching the owner's private repositories for applications and deciding which count, which R6 keeps out of this work; so the file was not created, the `dependents` check reports that there was nothing to run, and `OWNER-ACTIONS.md` asks the owner to list them and run the check. The upgrade path itself is exercised by `rust-rewrite/compat/`: every row of `docs/upgrading.md` is imported in its new form, every class, constant, function and member row is run once on Windows through a runner (a row with no runner fails the test), type rows are checked by the compiler, and rows of a macOS-only module are not run on Windows (D32; `OWNER-ACTIONS.md`, section 3).

## D21. Adding a user script does not wait; what the host asks of the page waits for it, in order

WebView2 registers a script added with `AddScriptToExecuteOnDocumentCreated` asynchronously, and a navigation started before the completion arrives can create its document without the script. The C++ library closed that race by pumping messages until the completion arrived. But WebView2 sends that completion only once a navigation already in flight has its response. When the response comes from a `Bun.serve` on the UI thread, the JavaScript that would send it cannot run inside the pump, so `bind`, `init` and `unbind` never returned; the C++ library hangs the same way (run against it in the same scenario). `add_user_script` now returns at once and counts outstanding registrations. Everything the host then asks of the page goes through one ordered queue in `sweetview-runtime/src/engine.rs`: `navigate`, `setHTML`, `eval`, a binding's reply and the bridge's bind and unbind notices. While a registration is outstanding, or anything is held, they are held in the order asked and carried out on the turn after the last completion, which is where they ran when adding a script waited. Without this, an `eval` right after `navigate` and `bind` on a new webview ran in the blank document the held navigation was about to replace. A held navigation stops the one in flight (`ICoreWebView2::Stop`), which it would cancel anyway, so the completion arrives even when that navigation would never get its response, as inside a blocking `run()`. A held evaluation stops nothing. A script added by `init` or `bind` is in every document from a navigation asked for after the call returns.

Alternative left open: keep the wait and let the page's response make progress meanwhile; Bun's event loop cannot be run from inside a native call, so this has no implementation. A narrower variant, holding evaluations only behind held navigations and not behind outstanding registrations, was not taken because it no longer matches where calls ran before.

## D22. The tab frame is `tao`'s undecorated window and answers its backdrop and DPI changes itself

The frame of a tabbed window is a `tao` window built with `with_decorations(false)` and `with_undecorated_shadow(true)`. The system keeps its resize border, shadow, snap, maximise and system menu, and the caption goes to the strip, so this project has no `WM_NCCALCSIZE` code; the proposal's fallback (a window this project creates itself) was not needed. The strip and every tab are `wry` child webviews of the frame; the pane windows of the old code have no counterpart, and a tab moves between windows with `reparent`.

The tab context menu is this project's own synchronous popup (`CreatePopupMenu` and `TrackPopupMenu` with `TPM_RETURNCMD`, in a menu destroyed on drop), not `muda`'s. The tabs library needs the chosen item before the call returns; `muda` 0.22's `show_context_menu_for_hwnd` is an `unsafe fn` that returns only whether something was chosen and reports which item later through its process-wide `MenuEvent` handler.

Activation comes from the existing window subclass (D8) as `WindowEvent::Activated`. The backdrop and `WM_DPICHANGED` are answered by a second subclass procedure on the frame (`FrameMessages` in `sweetview-platform-window`), so the subclass every window has stays as it is:

- `WM_ERASEBKGND` fills the strip's rectangle (its height at the window's DPI) and the page's rectangle with two owned solid brushes: `#e9eaee` and `#f9f9fb` light, `#292a30` and `#15161a` dark, as the old frame painted them. The brushes are replaced when a frame that follows the system changes theme. `tao` paints one background colour.
- `WM_DPICHANGED` goes to `tao` first, so it records the new scale, then the rectangle the system suggests is applied. `tao` keeps its own size when the scale is unchanged and computes one from the old inner size otherwise.

Alternative left open: arms for both messages in the subclass in `windows.rs` (one procedure, but every window would carry tab-frame state), or `muda`'s context menu with its event channel (an asynchronous tab menu).

## D25. Windows Sweetview did not make are lent per call, never kept as a handle

The runtime keeps an adopted window, and a window a webview was given, as its handle value, and lends it to each platform call as a `BorrowedWindow<'a>` (`crates/sweetview-platform-window/src/windows.rs`). `BorrowedWindow::with_handle_value` checks the value with `IsWindow` and lends the window for one call; `BorrowedWindow::of` lends a `tao` window for as long as that window is borrowed. A `BorrowedWindow` is not `Clone` and not `Send`, so it cannot be kept. It replaces `ForeignWindow`, a cloneable value with no lifetime that the runtime kept for the whole life of every window (the review's F3). The OS validates the handle on every call made with it, which is what the SAFETY comments now say, and identity is checked where it matters: the subclass and the tab frame's procedure compare the state they installed (F29). The runtime lends per call through `with_native` and `with_mount_target` in `crates/sweetview-runtime/src/window.rs`. The test `a_handle_value_is_lent_only_when_it_names_a_window` (`crates/sweetview-platform-window/src/windows_tests.rs`) destroys a lent window inside the call and shows the calls then fail.

Two rules follow from not keeping the window. Dropping `WindowIcons` never destroys icons a live window still shows: they are parked by the window's handle value and destroyed at the next `WindowIcons::set` of the thread after that window is gone, so an adopted window released while it shows icons Sweetview gave it keeps valid icons for its whole life (`an_adopted_window_keeps_valid_icons_after_it_is_released` in `crates/sweetview-runtime/src/window_tests.rs`, `icons_a_live_window_shows_outlive_their_owner_and_go_with_the_window` in `windows_tests.rs`). And a window is destroyed at once by `destroy_now`, which takes the `tao` window by value, except when it is disposed of from inside a `tao` call on it: then it is destroyed on the next turn, once that call has returned (`Core::destroy` in `crates/sweetview-runtime/src/window.rs`), the rule D16 keeps for webviews.

The same work merged the one-call window functions the review called a layer. `set_placement` replaces `set_outer_bounds`, `move_outer`, `resize_outer`, `set_topmost` and `refresh_frame`; `show_as` replaces `hide`, `minimize` and `toggle_zoom`; `press_frame` replaces `start_os_drag`, `move_with_mouse` and `size_with_mouse`; `send_close_for_tests` became `request_close`. `tao`'s `is_visible` is used for its own windows. Alternative left open: the owner's written acceptance of a stored handle with no lifetime, the other way the review offered to settle F3.

A popup menu is built by `muda` (items, check marks, icon bitmaps, submenus) and tracked by `show_popup` in `crates/sweetview-platform-window/src/popup.rs` with `TrackPopupMenu(TPM_RIGHTBUTTON | TPM_RETURNCMD)`, plus `TPM_BOTTOMALIGN` for the tray's menu and `popupMenuAtCursor`, as `win32/menu.ts` did before the rewrite. `muda` 0.22's `ContextMenu::show_context_menu_for_hwnd` is not used: it is `unsafe`, it passes `TPM_LEFTALIGN | TPM_RETURNCMD` only, so letting go of the right button over an item did not choose it and the tray menu could not open upward from the cursor (the review's F14), and it reports the item through the process-wide `MenuEvent` handler. ## D38. Native timers are messages a thread of the signal window posts, not `WM_TIMER`

The second review's G1: under the pumped loop, a tray menu opened from a deferred job sometimes delivered no native timer at all, neither an application's interval nor the pump's guard (D30). The mechanism, measured:

- Inside the real menu, traced with a `WH_GETMESSAGE` hook (every message a look at the queue returns, removed or not) and a `WH_CALLWNDPROC` hook: the menu loop's first look, which removes nothing, got `WM_PAINT` for `tao`'s hidden thread target although both timers were already due (`GetQueueStatus` showed `QS_TIMER` and `QS_PAINT`). `tao` keeps an internal paint request (`RDW_INTERNALPAINT`) pending on that window: after `NewEvents`, after each user event, and at the top of the procedure of every `tao` window for every message; and the window is `WS_VISIBLE` with `WS_EX_LAYERED`, so it receives `WM_PAINT` without being shown. The OS makes a `WM_TIMER` only after paint.
- The menu loop does not take another window's paint request: it counted the look as idle and sent `WM_ENTERIDLE` to the menu's owner. The tray menu's owner is a `tao` window, whose procedure renewed the paint request for that message, so the loop's second look got `WM_PAINT` again, and the loop then waited for new input. Due timers that a look has seen are not new input, and a timer that is due and not delivered does not come due again, so nothing woke the loop until some other message arrived: one posted, input, or another window's timer coming due afresh. The menu waited until then (0.3 to 0.6 s when an IME window's timer woke it), or until it was closed.
- Through the binding, on the tree before this work, 30 menus: 7 stalled; with 40 ms between the menu function and the menu, so that every timer is due at the first look: 28 of 30. One `WM_NULL` posted to the signal window 400 ms in revived every stalled menu (8 of 8; 18 of 18 with the 40 ms); posted to the menu's owner, which renews the paint request again, it revived none (0 of 18).
- With no Sweetview code, a plain Win32 program (a message-only window with two timers of 10 and 15 ms; a posted message whose handler waits 30 ms and calls `TrackPopupMenu`, owned by a hidden window): with a second window made `WS_VISIBLE | WS_POPUP` and layered as `tao` makes its target, and an owner whose procedure renews that window's internal paint request for every message, 40 of 40 menus waited before their first tick (median 531 ms). Take away any one part and none waits: the paint window hidden (0 of 40; this is why the review's experiment 1 as written found nothing: a hidden window gets no `WM_PAINT`), the owner not renewing (0 of 40: the first look takes the request away, and the second finds the timers), or the timers not yet due at the first look (5 of 40 without the 30 ms). `WM_NULL` to the owner: still 40 of 40; to the timers' window: 0 of 40, first tick at 65 ms.

The fix (`crates/sweetview-platform-loop/src/windows.rs`): a `SignalWindow` no longer uses `SetTimer`. A thread of its own, started with its first timer, posts `WM_SWEETVIEW_TICK` (the timer's id and the tick's number) when a timer comes due; timers due at the same wake are posted in the order they came due, and then in the order they were set (the third review's H5). Periods are held to 10 ms and above, as `SetTimer` holds them. A posted message is new input to a loop that waits, so every loop that dispatches the thread's messages delivers the ticks: a popup menu's, a dialog's, the OS's move and size loop, an application's own. Everything on the signal window's timers is covered: an application's timeouts and intervals, the hit-region poll, the tray's double-click timer and the pump's guard. Posting needs no `unsafe`, and `SetTimer` and `KillTimer` are gone from the crate.

A posted message also comes ahead of input and paint, which a `WM_TIMER` never did. With each tick posted again the moment it was taken, a 10 ms interval whose job took 15 ms always had its next tick queued when the job returned, and input and paint did not come out (the third review's H1). So:

- A timer's next period starts when its job returns, or unwinds. A job longer than its period leaves the rest of the queue a whole period before the timer's next tick. An interval whose job opens a modal loop does not tick again until the job returns; the other timers do.
- A tick taken while keyboard or mouse-button input waits (`GetInputState`) is handed back and posted again 1 ms later, for at most 100 ms after it came due, so the input is taken first, as it was ahead of a `WM_TIMER`. After that limit the tick runs whatever waits, so a loop that never takes some input still gets its timers.
- Paint is not waited for. Under the pumped loop `tao` keeps a paint request pending nearly always (the mechanism above), and deferring behind it cost a busy interval between a third and a half of its ticks.
- A tick posted and not taken within four periods (and at least 250 ms) counts as lost: a loop removed it without dispatching it, or the queue refused it. The timer's tick is posted again under a new number, and the lost one is dropped if it arrives later, so one lost tick does not end its timer (the third review's H4).

Measured for H1, a 10 ms interval whose job takes 15 ms while an application's own window, shown at a fixed place, is clicked with `SendInput` and asked to repaint, five times each (`packages/sweetview-native/test/fixtures/busy-interval-input.ts`; the longest waits, in ms, and in brackets the longest after the first click, which also waits for the window to come to the front):

| the next period after the job | 74 (1), 16 | 34 (16), 0 | 64 |
| that, and input first (taken) | 54 (2), 16 | 32 (16), 0 | 64 |
| that, and paint first as well | 30 (1), 0 | 35 (16), 0 | 41 |

Through the runtime (`a_busy_interval_leaves_paint_its_turn_in_both_loop_modes`, `tao` asked for a paint every 40 ms, 800 ms): on `5b0388d` a paint waited up to 261 ms under the pump, where a pump took up to 339 ms, and up to 141 ms in the blocking run; now up to 16 ms (one job). With paint first as well, 13 ticks under the pump instead of 29. The menu probe with the design taken: 0 of 300 menus without a tick, in each mode; with the next period after the job alone, 0 of 100 in each.

The thread and the end of the application. The release at the end (D36) ends the thread once no timer is left, waiting at most 20 ms for it; a later timer starts a new one. Dropping the window waits for nothing: it sets the thread's own stop flag (one per thread, so a thread left to end never ticks beside its successor: the third review's H6), wakes the thread under the lock when the lock is free (else the thread looks at its flag again within 100 ms), and lets its handle go; the thread owns what it uses, and the window's drop disarms its `Poster`. What changes for an application: a timer's tick no longer waits behind paint; it waits behind keyboard and mouse-button input for at most 100 ms; an interval's period is counted from the end of its job, as a `WM_TIMER`'s was not; and an interval whose job opens a modal loop pauses until the job returns.

## D39. A message window confirms its own destruction, and a `Poster` posts only the application's range

The second review's G3: a `WM_NCDESTROY` posted to a live `MessageWindow`, by `Poster::post(0x0082, ..)` from safe code or by another process of the session, made its procedure disarm the owner for good. A window procedure cannot tell that message from the one `DestroyWindow` sends. Measured on a message-only window: `IsWindow` reads true in both, before and after `DefWindowProcW`, and `InSendMessageEx` reads 0 in both; a `WM_NCDESTROY` sent from another thread reads `ISMEX_SEND`. (At `DestroyWindow`'s own `WM_NCDESTROY` the window had no next sibling, where a posted one still had one; that is undocumented and depends on another window existing, so it is not used.)

So (`crates/sweetview-platform-loop/src/windows.rs`):

- `Poster::post` posts only `WM_APP` to `0xBFFE` and refuses every other number. Every caller in the tree posts `WM_APP` plus a constant. A system message posted through it would be acted on as if the OS had sent it.
- A `WM_NCDESTROY` sent from another thread is answered and changes nothing: `DestroyWindow` destroys only windows of the calling thread.
- A `WM_NCDESTROY` of the window's own thread marks its post target `ending` and posts the window `WM_STILL_ALIVE` (`0xBFFF`, kept by the crate). While `ending`, posts are held, never sent, so none reaches a handle value a destroyed window gave up, and a poster that finds `IsWindow` false disarms the target and reports failure. The next message the window receives proves it alive: it is armed again and the held posts are sent. A window `DestroyWindow` destroyed takes its queued messages with it, so its confirmation never arrives; the test asserts that the queue holds none after a real destruction. `Drop` during `ending` destroys the window only when its own confirmation is still queued for it.

`QueuedMessage::dispatch`'s SAFETY comment no longer says a message's parameters are the OS's own. They are the poster's, any process of the session may post, and the window procedure reads them as the message defines. For a `WM_TIMER` naming a timer procedure, measured: `DispatchMessageW` of one posted with the address of a function this thread never registered called it 0 times; the same function registered with `SetTimer` was called; after `KillTimer`, the posted one called it 0 times again.

Tests: `a_posted_ncdestroy_leaves_the_window_and_its_owner_working` (a wake made while unconfirmed is held and delivered, the owner arms again, its timers tick and its `Drop` destroys the window), `an_unconfirmed_ncdestroy_still_lets_drop_destroy_and_a_sent_one_is_refused`, and `a_window_destroyed_by_other_code_disarms_its_owner`, with the new assertion that no confirmation is left queued.

Added after the third review (H3, H4). The table entry and post target of a window that other code destroyed outlive it while `ending`, so a later `MessageWindow` that the OS gives the same handle value could meet them: its creation messages ran the old closure and armed the old target again, and the old owner's `Drop` then destroyed the new window. An entry is added only after `CreateWindowExW` returns, so one found at a creation message (`WM_GETMINMAXINFO`, which a message-only window gets even before `WM_NCCREATE`, measured; `WM_NCCREATE`, `WM_NCCALCSIZE`, `WM_CREATE`) while this thread is inside `MessageWindow::new`'s `CreateWindowExW` is stale: its owner is disarmed and the entry forgotten before anything of the new window runs. Outside that, the same numbers, which anyone can post, reach the owner as usual. And a post that the queue refuses when held posts are sent (a full queue) stays held, and goes out first, in order, with the next post or the next message the window gets. Tests: `a_stale_entry_under_a_new_windows_handle_value_is_forgotten_at_its_creation` (a `WH_CBT` hook plants the entry a destroyed window would have left under the new window's handle value: on the rule that looked only at `WM_NCCREATE` the planted closure ran, at `WM_GETMINMAXINFO`) and `a_held_post_the_queue_refuses_stays_held_and_goes_out_in_order` (the thread's queue filled to its limit).

Alternative left open: keep treating every `WM_NCDESTROY` as the destruction and accept that a stray post disables the window, which is the safe direction for memory and the wrong one for the owner.

## D40. A pump inside a running loop does nothing, and the pump's guard is a value that cancels itself

The second review's G2: a `pump()` called from a callback while a pump was running (`pumpEvents()` from JavaScript) posted a user event, set a second guard timer over the first in the runtime's one cell, and cancelled that second one when `run` refused it, so the outer pump's timer stayed set with no owner and the outer pump went on unguarded; and an unwind out of `run_return` skipped the cancel. `Runtime::pump` (`crates/sweetview-runtime/src/runtime.rs`) now returns `true` at once when either loop mode is running, which is what its contract and the binding's have always said, so a nested call posts and sets nothing (also under `run_blocking`). ## D43. The public calls upgraded applications needed, so none reaches into internals or its own `bun:ffi`

An upgraded application uses the library as designed, with no workaround and no internal import, so the library offers both. This acts on the alignment option D35 left open.

- `Menu.popup(owner, menu, at?, options?: MenuPopupOptions)`, with `MenuPopupOptions = { above?: boolean }`: `above: true` puts the menu's bottom-left corner at the point (or the cursor), so it opens upward. ## D46. A window leaves the screen before its webview goes, and what shows where no page is drawn is the window's backdrop

The defect: at Quit from a tray, a framed window with a dark page stayed on the screen for a moment with its frame, title bar and taskbar button and its whole client area white, then went with the process. Measured before the change on this machine (Windows 11 26300, a 30 Hz display, so the screen is read once per displayed frame: a read waits for the next composition, 33 ms whatever its size, from any number of threads), by a second process reading the window's client area from the screen from launch to exit (`packages/sweetview/test/fixtures/window-watch.ts`), quitting from inside through a preload that calls the application's own quit, no input: `demos/web-app` showed a white client area (`#f8f8f8` over all of it) in its last frame on the screen in both runs, and white over 93 to 96 % of it for 2 frames at start in one; `desktop-pet`'s framed settings window (`PET_OS_FRAME=1`) 1 white frame at Quit; `native-tabs` and the frameless settings window none. The longest run was 2 frames (66 ms), at start; at Quit 1 frame each time, because the process ends about 40 to 90 ms after Quit. A slower machine or a longer cleanup after `run()` makes it longer: with a second `run()` after the first, the window stayed white for 22 frames; with a webview disposed and a new one attached, 40.

The cause:

- `run()` returning tears its own webview down (`shutdown()` in `packages/sweetview/src/app.ts`), with its window still on the screen; since D36 the window goes only when the process ends. In between, nothing covers the client area.
- A window without tabs had no background: `tao`'s window class has no brush and Sweetview gave `tao` no background colour, so its client area was never painted, and what shows of an unpainted client area here is white. WebView2's own default background is white too, until its page paints.
- The release at the end of the application destroyed the webviews (step 2 of D36) before the windows (step 6), with nothing hiding the windows first; `Window.dispose()`, `app.dispose()` and a tabbed window's teardown also destroyed the webviews of a visible window before the window.

Before the Rust rewrite (0.x), from what the tree records (`rust-rewrite/reference/`, D36): an application ended with `notifier.dispose(); tray.dispose(); app.dispose(); process.exit(0)` after `run()`; `run()` destroyed its webview with the C++ library's `webview_destroy` while the window was visible, and `app.dispose()` destroyed the window a few lines later with no message pumped in between. The same gap existed, shorter by the release's work; whether it was ever seen white is not recorded, and was not measured here.

What was built:

- Every path that destroys a window hides it first, then destroys its webviews, then the window: `Window.dispose()` (its dispose hooks are the webviews' teardown), `app.dispose()` (it disposes the window first outside `run()`), a tabbed window's teardown (`disposeHost` in `packages/sweetview/src/tabs/win-tabs.ts`), a window disposed inside `run()` (hidden at once; destroyed when `run()` unwinds), and the end of the application: a new `conceal` kind first among the releases in `packages/sweetview-native/src/lifetime.ts` and a step hiding every window before the webviews in `crates/sweetview-runtime/src/lifetime.rs`. The hide is the first instant of a destroy that follows in the same step; no close, dispose or quit ends in a hidden window.
- `run()` returning hides its window before destroying its webview. The window itself stays alive, as D36 has it, for code after `run()` and a second `run()`, and is destroyed when the process ends, a few milliseconds later for an application whose last line is `run()`. A later `run()` of a webview attached to that window shows it again (with `showOnReady`, once its page is ready); the application's own `show()` or `hide()` in between takes over. Not destroying the window there keeps both: a window a second `run()` reuses is not taken away, and no window is seen empty.
- What a window shows where nothing has painted is one colour, resolved once in `crates/sweetview-runtime/src/window.rs` when the window is made: its `backgroundColor` (the public option of D43), or with none its appearance's page colour, `#15161a` dark, `#f9f9fb` light, the colours a tab frame's page area already had (`appearance: "system"` takes the theme `tao` gave the window). A transparent window, and a colour-keyed one given no colour, show through as they always have. The webview made in a window starts with that colour as WebView2's default background (`backdrop_of` in the same file, read by `crates/sweetview-runtime/src/engine.rs`; a tab's is its tabbed window's page colour), so a page that has not painted yet, or a window whose webview has gone while the window stays (a webview replaced, the last tab disposed while an `onClose` listener keeps the window), shows that colour, never white. D43's branch had set the webview's colour a second time from TypeScript after it was made (`packages/sweetview/src/app.ts`, and a `backgroundColor` tab hook in `win-tabs.ts`), only when the option was given; that duplicate of the runtime's colour is removed, and the option keeps its name, documentation and effect. The system theme is read from `tao`, not from WinRT's `UISettings`: making a `UISettings` for every window made the runtime's release test crash afterwards (an access violation, every run); why is not known, and a tab frame of appearance `"system"` still makes one (`TabState::new`).
- `wry` 0.58.2 destroys the container window of a webview made with `build_as_child` only; one made with `build`, which fills its window, left its `WRY_WEBVIEW` container behind until the window was destroyed, one USER object more for every webview a window had. Found by the test of a webview replaced in a window that stays. `sweetview_platform_webview::drop_filling` drops the webview and then destroys its container while it is still a child of the same parent (three `unsafe` blocks of one call each); `tests/drop_filling.rs` measures 5 USER objects left over 5 lives by a plain drop, 0 by `drop_filling`.
- The audit of every close, dispose, quit or release that ends in a hide rather than a destroy (`hide()`, `set_visible(false)`, `SW_HIDE`, `show_as`) in `packages/` and `crates/`: `closeToTrayOnLastWindow`, which hides the last visible window by its documented contract, unchanged; `Window.hide()`, `toggle()` and the tab driver's frame `hide`, which only do what the application asks; a tab hidden when another is selected or while it is moved between windows, which stays open; the end of a blocking `run()` (above), which hides its window and leaves it to the end of the process; and `windowChromeMethods`' close button, whose default hides the window rather than closing it. That last one contradicts "a closed window is destroyed"; making it close needs a close request on `Window` that the public API does not have, a new public call, which is the owner's to decide: unchanged here. The pending-destroy list (a window disposed from inside a call into `tao` that holds it) destroys the window on the next turn or in the release, as before; `Window.dispose()` hides it at once.
- Not changed, for the owner: a pumped loop whose application failed to start with its error caught (`demos/native-tabs` when its first tab fails) never ends, and the demo still quits by hand. The cause, measured: Bun keeps a process waiting on an unsettled top-level `await` alive whatever its timers, so `await runEventLoop()` holds it until `quitEventLoop()`, and Bun reports none of the application's own pending work (`process.getActiveResourcesInfo()` answers `[]`), so the loop cannot tell a failed start from an application between two windows. A rule tried here (the loop ends at the first pump at which the application has nothing a person can reach, once it has had something) ended the loop of `rust-rewrite/compat/fixtures/rows-desktop.ts`, which disposes one row's windows and, after an `await`, makes the next row's: an application doing the same would lose its loop. Any automatic end changes when an application's process ends, which is the owner's decision; it was taken out.
- Held back on macOS by D42's predicate, each a row of `rust-rewrite/HANDOFF-macos.md` section 8: the hide before a teardown (`concealWindow` in `window.ts`, the end of `run()` and its restore, `app.dispose()`'s order in `app.ts`). Nothing here is exported for an application: the hide and the run-end mark are module-private, and no call was added to `./internal`.
- The demos reveal their windows through the ready signal: `showOnReady` with a `readyTimeoutMs` watchdog, and each page calls `signalReady()` once it has rendered (`web-app` from its first React effect, with `appearance: "dark"` for its dark page; `desktop-pet`'s pet on its first drawn frame, its settings window at start only with `PET_SETTINGS=1`; `native-tabs`' first tab). WebView2 renders and runs the page's frame loop while its window is hidden (the pet's first frame signals ready about 0.6 s after launch), so the window appears with its page drawn. The examples in `README.md` and `docs/app.md` do the same. `docs/app.md` says what a person sees at Quit and in which order things go.

Measured after the change, the same way: 0 frames with a white or light flat client area in every window of `web-app` (two runs), `native-tabs` and `desktop-pet` (framed and frameless settings window), at start and at Quit; each demo's last frame on the screen shows its page; Quit to process exit 36 to 104 ms.

Tests: `packages/sweetview/src/quit-flash.test.ts` runs `test/fixtures/quit-flash.ts` (a framed window with a dark page, `appearance: "dark"`, revealed on ready) in a process of its own with the watcher in a second one, for a quit from inside the blocking `run()` with a worker, the pumped loop, `app.dispose()` and the window's dispose inside `run()`, two runs one after the other, a webview replaced, and the last tab of a tabbed window disposed while the window stays. It asserts that no frame shows the window light (a colour of luma 200 or more over half of it or more), that the window is off the screen in the last frame its webview was there, that a window left without a page shows the dark backdrop or its page only, and that the release destroyed the window before the process ended. On the base commit all seven fail (1 white frame for each quit; 22, 40 and 110 light frames for the others). `packages/sweetview/src/window-reclaim.test.ts` runs `test/fixtures/window-reclaim.ts`: with a main window open, it opens and closes a second window with a webview 30 times by each path (`WM_CLOSE` to it with no `onClose` listener, `dispose()`, `app.dispose()`, a tab opened and closed in a tabbed window that keeps another), and asserts that every closed handle fails `IsWindow`, that, measured twice after 10 warm-up rounds (rounds 10 to 20 and 20 to 30, the smaller growth of each count judged, as `smallest_growth` does, since an object WebView2 or the shell makes once in the process shows in only one), USER and GDI objects and the WebView2 processes descending from the process do not grow, and kernel handles grow by at most 1.2 per window a webview was made in plus 2 (`tao` and `wry` alone keep 6 over 5 lives; measured 19 to 25 over 20 windows in six runs, 77 over 75, and -1 to +1 for tabs, which make no window), and that private bytes do not climb (the median of the last ten rounds within 12 MB of the first ten; the largest allocator step over 80 rounds was 8 MB, with no climb). Measured once, the test failed twice in eight runs on such a one-time object (a USER object with a WebView2 process started meanwhile; one kernel handle over 20 tabs)

Alternatives left open:

- Destroying the window too when `run()` returns. It removes the hidden window from the process sooner, but takes from an application a window it may run again (D36, R1). Not taken; the process ends milliseconds later anyway.
- Leaving the webview alive when `run()` returns and destroying it with the window at the end of the application. Nothing would be empty at any moment, but `run()` would no longer tear its webview and worker down, as it always has and the docs say.
- `showOnReady: true` as the default for `createApp`, and a placeholder while a page loads (the window's backdrop is one already; an image, or a small native splash window, would be others). Product decisions for the owner; not built.

== The frame: decisions this item rests on ======================================

- The frame is tao's window with with_decorations(false) and
  with_undecorated_shadow(true): the system keeps its border, shadow, snap,
  maximise and system menu; no WM_NCCALCSIZE handling of this project's.
- The backdrop and a DPI change are answered by a second subclass procedure of
  the frame (FrameMessages in crates/sweetview-platform-window/src/tab_frame.rs):
  WM_ERASEBKGND fills the strip's rectangle (40 DIP at the window's DPI) and the
  page's rectangle with two owned solid brushes, light or dark, swapped when a
  "system" frame's theme flips; WM_DPICHANGED is passed on to tao first (it
  records the new scale, so the default minimum, a logical size, follows it)
  and the suggested rectangle is applied after it. tao alone kept its own size
  when the scale was unchanged and worked one out from the old inner size
  otherwise: that was a defect of the rebuild against this list, fixed here.
- The tab context menu is this project's own synchronous popup
  (TrackPopupMenu with TPM_RETURNCMD), and activation comes from the existing
  window subclass.

== Not run, and why =============================================================

- A real DPI change: the machine has one monitor at one scale, so
  WM_DPICHANGED was sent to the fixture's own frame (and to a test window in
  cargo test) carrying the window's current DPI and a suggested rectangle. The
  rectangle is proven applied; the strip height and the default minimum were
  read at that same scale, so their following a different scale rests on the
  code (both are computed from the window's DPI at the time of the call) and
  not on an observed change of scale.
- strip.scrolled has no check of its own: it stores how far the strip's tabs
  are scrolled, which only the drop index of a tab dropped on a strip with
  more tabs than fit reads; the drop-on-strip check uses a strip whose tabs
  all fit (scrolled 0), and dropIndex's use of the offset is covered by the
  unit tests in strip-shared.test.ts.
- NotifyParentWindowPositionChanged is proven by a counter in the engine
  (Engine::moves_told, a test hook), not by an OS reading: WebView2 keeps the
  position it was told to itself.
- The hosted CI runner does run the OS move loop for injected input (its
  control read ok), but applies a move later than this machine, and its
  screen is small. The gesture checks were changed for both (see "Runs");
  their run on the runner after that change is not part of this file. The
  small screen was proven here only by laying out in a 1024 x 768 area of a
  larger screen (SWEETVIEW_TEST_SMALL_SCREEN=1), not on a 1024 x 768 display;
  in that mode a maximised window still spans the real screen.

2. What is independent of the webview was run: the demo's notifier flow (its tray with TRAY_ICON, its
   createNotifier onClick and its send(), from @n1h/sweetview/native), plus a native notifier driven
   through the binding's debug hooks so the toast click and the forced-fallback balloon click arrive
   from the UI thread's loop deterministically. The probe (kept out of the tree, in the ignored
   rust-rewrite/local/w55-notify-probe.ts) is, in short:

     const tray = createTray({ tooltip: APP_NAME, icon: TRAY_ICON, menu: () => [...] });
     const notifier = createNotifier({ onClick: ({ id, data }) => log(`Clicked ${id}, sent at ${data.sentAt}`) });
     notifier.notify({ id: "menubar-notify-1", title: APP_NAME, body, data: { sentAt } });  // real WinRT toast
     const backend = createNotifier({ onClick: same });  const native = debugNativeNotifier(backend);
     native.debugShow("menubar-notify-toast", ...)  -> toast:<cookie>; debugSimulateToastEvent(cookie, "activated"); pump
     native.debugForcePath("balloonOnly");
     native.debugShow("menubar-notify-balloon", ...) -> balloon:<uid>; debugSimulateBalloonEvent(uid, "clicked"); pump
     dispose all; print debugLiveToastHandlers()

click and the balloon-fallback click each reached the demo's onClick with the id and the parsed
data; every WinRT handler was released after dispose; the compiled executable carries the binding
(no file beside it) and behaves the same.

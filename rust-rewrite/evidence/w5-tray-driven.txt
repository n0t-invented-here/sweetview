W5.5, the tray part: demos/menubar-only run from source and from its compiled executable, its tray icon
driven with the messages the shell posts (no physical click; see below), on Windows 11, 2026-11-27.

Driver: demos/menubar-only/scripts/tray-drive.ts. It starts the app, finds the app's tray-icon window
(class tray_icon_app, in the app's process), posts WM_RBUTTONDOWN/WM_RBUTTONUP in the callback message
tray-icon registers the icon with (6002, mouse message in lParam), reads the popup menu back from the OS
(MN_GETHMENU, GetMenuStringW, GetMenuState) and posts key presses to the popup menu window.
A click by hand cannot be done by an agent; the posted messages are what the shell posts for one.

== From source ==
$ cd demos/menubar-only && bun scripts/tray-drive.ts . bun run app.ts
started: bun run app.ts
tray icon window found (class tray_icon_app) in the app's process
right click -> menu: ["Up for 0 s [disabled]","----","Clock in Tooltip","----","Quit Menubar Only"]
Escape -> menu closed, nothing chosen
right click again -> menu: ["Up for 1 s [disabled]","----","Clock in Tooltip","----","Quit Menubar Only"]
Down, Down, Return -> chose 'Clock in Tooltip'
right click again -> menu: ["Up for 2 s [disabled]","----","Clock in Tooltip [checked]","----","Quit Menubar Only"]
Down, Down, Down, Return -> chose 'Quit Menubar Only'
process exit: 0
stderr: (empty)

What it shows: the menu is built from the function form on every open (the "Up for" line counts up, the
check mark follows the app's state), separators and a disabled item are on the real menu, Escape chooses
nothing, a chosen item runs its click handler (the check mark flips; Quit ends runEventLoop and the process
exits 0), and the compiled executable carries the binding with it.

Not covered here: demos/menubar-notify, which depends on the notifier (W5.3) and is integrated separately.
Left click, double click and the TaskbarCreated re-add are covered by bun tests in
packages/sweetview-native/src/win32/tray-menu.test.ts.

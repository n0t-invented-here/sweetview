# Handoff to the macOS goal

Written by the Windows goal for checklist item W10.3. Read it after `rust-rewrite/REQUIREMENTS.md` and before starting `rust-rewrite/CHECKLIST-macos.md`. Every claim about code names its file; line numbers are those of the commit named below. "Not confirmed" marks what was not checked; "suggestion" marks this document's own proposals.

The first thing to run on a Mac, before any macOS work: `rust-rewrite/VERIFY-macos.md`, a prompt for an agent there that checks the head against the tag `pre-rust-rewrite` on macOS and writes its report into the run-output folder on that machine, which git ignores (run output is kept outside git).

## 1. Where things stand

On Windows, Sweetview's native layer runs on Rust: the crates under `crates/`, reached from Bun through one N-API binding (`packages/sweetview-native/prebuilt/sweetview.win32-x64-msvc.node`, loaded by `packages/sweetview-native/src/binding.ts`). Windows no longer loads `@n1h/sweetview-webview-bun` or the C++ library, and no Windows source under `packages/` imports `bun:ffi`. macOS still runs today's code: the TypeScript under `packages/sweetview-native/src/darwin/`, the files `packages/sweetview/src/darwin-*.ts` and `packages/sweetview/src/tabs/darwin-*.ts`, calling AppKit through `bun:ffi` and the webview through the C++ library of the optional peer `@n1h/sweetview-webview-bun`. Where the Windows goal changed shared TypeScript in a way that would run on macOS and has not been run on a Mac, macOS is held on the tag's path behind `macosKeepsTagPath()`; section 8 lists each place, for the macOS goal to turn on deliberately. The work is on branch `v1-rust-rewrite` of `n0t-invented-here/sweetview`; tag `pre-rust-rewrite` marks the tree before the first change. This document describes the tree at the end of the Windows goal (`rust-rewrite/CHECKLIST-windows.md`); its line numbers are those of commit `ea51374`. The Windows items it builds on include tabs (W7.1, W7.2), the docs and upgrade items (W9.1 to W9.4), the unsafe ledger (W10.1), `bun build --compile` embedding the binding (W1.6), the window and notifier demos (W4.7, W5.5), the GitHub Actions workflow (W0.6), `rust-rewrite/OWNER-ACTIONS.md` (W10.4) and the independent review of every `unsafe` block and every item's evidence (W10.2). This document was first written at commit `f88ceb4`; the review's findings, fixed after that, renamed and reshaped several things it describes (section 7, last bullet).

## 3. What is stubbed

### 3.0 The gate, and what to do about it

W10.3 asked for stubs behind `cfg(target_os = "macos")`. The code does not use that gate: every platform crate selects its implementation with `#[cfg(windows)]` and its stand-in with `#[cfg(not(windows))]` (the one exception is `crates/sweetview-platform-input/src/permissions.rs`, which gates on `target_os = "macos"`). So today the stand-ins serve macOS and Linux alike.

Suggestion for the macOS goal: replace each `#[cfg(not(windows))] #[path = "unported.rs"] mod platform;` with three arms, `#[cfg(windows)]`, `#[cfg(target_os = "macos")]` (the new macOS module) and `#[cfg(not(any(windows, target_os = "macos")))]` (the stand-in, kept for Linux), and do the same for each `cfg(not(windows))` fallback function in `sweetview-runtime`. Gate each crate's macOS dependencies the same way (`[target.'cfg(target_os = "macos")'.dependencies]`). That keeps `cargo check --target x86_64-unknown-linux-gnu` meaningful for the Linux goal and records in `rust-rewrite/HANDOFF-linux.md` (item M9.4) which stand-ins are still Linux's.

Every platform crate's `Cargo.toml` puts its OS crates under `[target.'cfg(windows)'.dependencies]`: `windows` in each; `windows-registry` 0.6.1 in `sweetview-platform-notify` and `sweetview-platform-shell` (D23); `dirs` 7.0.0, `webview2-com` and `windows-core` in `sweetview-platform-webview` (`dirs` for the default WebView2 profile folder, D15, D23). Both new crates are declared once in the root `Cargo.toml` `[workspace.dependencies]` (lines 30 and 35). `sweetview-platform-loop` is a Windows-only dependency of the notify, shell and webview crates (for `MessageWindow`, `Poster` or the pump calls, each as it needs) and an unconditional one of `sweetview-platform-window`, whose `HandleCounts` is the loop crate's `ResourceCounts` (`crates/sweetview-platform-window/src/lib.rs` line 132). `sweetview-runtime/Cargo.toml` depends on `tao`, `wry`, `muda`, `rfd` and `tray-icon` unconditionally, and on `webview2-com` for Windows only. `sweetview-platform-window` has a `test-support` feature that the runtime enables as a dev-dependency only; the module it switches on, `src/test_support.rs`, reads back what the OS shows and compiles on Windows only (`src/lib.rs` lines 140-144). `dirs` is cross-platform; whether the macOS data store of D15 needs a folder from it is not confirmed.

In the tables below, "same signature" means the macOS module must expose exactly these items, because `sweetview-runtime` calls them on every platform.

### 3.1 `sweetview-platform-loop`

Gate: `src/lib.rs` lines 25-30 (`#[cfg(windows)] #[path = "windows.rs"] mod platform;` / `#[cfg(not(windows))] #[path = "unported.rs"] mod platform;`); exports on every platform at lines 34-36: `discard_quit, dispatch_waiting, messages_waiting, peek_without_removing_for_tests, post_quit_for_tests, resource_counts, SignalWindow, Waker`. Lines 37-38 export on Windows only, with no stand-in: `next_message, wait_message, MessageWindow, Poster, QueuedMessage, Waited, WindowError` (D23: one owning type for a message-only window and its cross-thread poster, and the pump calls, used by the Windows modules of the notifier, the single-instance window and the clipboard owner, and by Windows tests). The macOS goal needs no counterpart for them unless its own modules choose to share one.

What these Windows-only items guarantee now (`src/windows.rs`): `QueuedMessage::dispatch(self)` (line 398) consumes the message, so one is dispatched at most once. `MessageWindow`'s window procedure answers `WM_CLOSE` itself (line 346), so a close posted from another thread or process does not destroy the window; should code of the thread destroy it anyway, `WM_NCDESTROY` disarms the owner (line 337): posts fail, timers and lent handles are refused, and its `Drop` destroys nothing (type documentation, lines 158-162). The process-wide table of registered window classes is a `OnceLock` (line 62), the form of global state D31 holds every crate to. A macOS module that owns a run-loop source or a port the same way should give the same three guarantees (suggestion).

Shared, no gate: `ResourceCounts` (`src/lib.rs` lines 42-51; its fields are documented as `GetGuiResources` and `GetProcessHandleCount`), and `src/testing.rs`: `settled_counts`, `smallest_growth` and `Growth` (D20's way of reading counts once they stop moving and taking the smaller growth of two runs, built on `resource_counts`), and `assert_gives_back_every_handle(rounds, round)` (line 73), the check `UNSAFE-POLICY.md` asks of every owning type: the round runs once, then `rounds` times measured twice, and each of the three counts must be back at its starting value. `LoopHost` (`src/loop_host.rs`) is shared and has no gate except its tests (`#[cfg(all(test, windows))]`, line 73); it keeps a clone of the loop's window target (D4, rewritten by D23, no `unsafe`), and that clone type-checks for `aarch64-apple-darwin` (section 2). `src/com.rs` line 58 has a `cfg(not(windows))` `ComApartment` whose `enter()` returns `Ok` (correct for macOS: no COM). On Windows the apartment is entered once per thread (D27): the runtime enters one when it starts (`crates/sweetview-runtime/src/runtime.rs` line 116), and the webview crate enters one the first time it makes an environment on a thread and keeps it for the thread's life (`crates/sweetview-platform-webview/src/windows/environment.rs` lines 31-50, `enter_apartment_once`).

### 3.2 `sweetview-platform-webview`

### 3.4 `sweetview-platform-window`

Gates in `src/lib.rs`: lines 83-88 (`#[cfg(windows)] #[path = "windows.rs"] mod platform;` / `#[cfg(not(windows))] #[path = "unported.rs"] mod platform;`, `pub use platform::*;` at 90) and lines 95-100 (`#[cfg(windows)] #[path = "tab_frame.rs"] mod tab_frame;` / `#[cfg(not(windows))] #[path = "tab_frame_unported.rs"] mod tab_frame;`, `pub use tab_frame::*;` at 102). The rule the crate follows since the review (D25; crate header, `src/lib.rs` lines 1-18): nothing outside an owning type keeps a window handle. A window Sweetview made is a `tao::window::Window`; any other window (an application's own, adopted or with a webview mounted in it, a webview's reparent target, the owner of a popup menu, the tray menu or a folder dialog) is kept as its handle value and lent again for each call as a `BorrowedWindow<'a>`. The former `ForeignWindow` and `OwnerWindow` are gone.

## 9. The webview is no longer built by `wry` (D47)

On Windows `sweetview-platform-webview` now makes the webview itself, as the C++ library's `win32_edge.hh` makes it, and `wry` is a dependency of no crate. This supersedes what sections 2 and 3 say about the webview and `wry`: the `sweetview-platform-webview` row of the crate table, the paragraph on dependencies (`sweetview-runtime` no longer depends on `wry`; `sweetview-platform-webview` now depends on `sweetview-platform-window` on every platform), the rows on `WebviewExtras::attach(&wry::WebView, ...)` and the free `set_background_color`, the note on `move_focus` (it is back, as `Webview::move_focus`), and the engine row on `reparent(&WebView, ...)`. With `wry` gone, `mac-check` no longer compiles `objc2-exception-helper`.

What the macOS goal inherits: the runtime's engine (`crates/sweetview-runtime/src/engine.rs`) calls the same types on every platform, so a macOS module of `sweetview-platform-webview` meets these signatures (the stand-in, `src/unported.rs`, has them now and returns `ErrorCode::Unspecified` or does nothing):

# Files under packages/ and demos/ that still import bun:ffi, one per line as path<TAB>reason (rust-rewrite/REQUIREMENTS.md, R3).
# After the Windows goal: macOS-only source that macOS runs on until the macOS goal, and probes. No setup entries.
packages/sweetview-native/src/darwin/activation.ts	macOS only: the custom URL scheme handler (NSAppleEventManager) and the single-instance hand-off over a CoreFoundation message port, until the macOS goal moves them to the binding
packages/sweetview-native/src/darwin/core-foundation.ts	macOS only: the CoreFoundation calls (run loop modes, strings, data) the other macOS files share, until the macOS goal
packages/sweetview-native/src/darwin/event-loop.ts	macOS only: the AppKit event loop pumped from Bun (finishLaunching, nextEventMatchingMask, sendEvent), until the macOS goal
packages/sweetview-native/src/darwin/notifier.ts	macOS only: notifications through UNUserNotificationCenter and its click delegate, until the macOS goal
packages/sweetview-native/src/darwin/objc.ts	macOS only: the Objective-C runtime bridge (objc_msgSend, classes, selectors, blocks) every macOS file calls through, until the macOS goal
packages/sweetview-native/src/darwin/window.ts	macOS only: NSWindow windows, overlays, hit regions and their observers, until the macOS goal
packages/sweetview/src/darwin-webview-host.ts	macOS only: the webview host over the C++ webview library of @n1h/sweetview-webview-bun (UI dispatch, request handler and file drop callbacks), until the macOS goal
packages/sweetview/src/darwin-webview-lib.ts	macOS only: opens the C++ webview library's symbols, until the macOS goal
packages/sweetview/src/darwin-worker-wake.ts	macOS only: the worker opens the webview library a second time to wake the UI thread with webview_dispatch, until the macOS goal
packages/sweetview/src/tabs/darwin-webview.ts	macOS only: the WKWebView helpers of the macOS tabs (hosting a webview in a tab, its delegates), until the macOS goal
packages/sweetview-native/test/win32-os.ts	probe: the Windows tests' shared reader and driver of OS state: window styles, rectangles, icons, layered attributes, monitors, open menus and dialogs, GDI and USER object counts, and messages and WM_DROPFILES drops sent to this process's own windows, plus a window of the application's own with its own window procedure; no Sweetview API reports these OS facts, and the own window proves Sweetview serves a window it did not make
packages/sweetview-native/test/fixtures/win32-probe.ts	probe: reads OS state of the webview fixtures that Sweetview has no API for (a window's text, client size, style, tracking bounds, visibility, DPI and dark title bar, a screen pixel, a process's top-level window, the foreground) and posts WM_CLOSE to, or taps one key into, a window of the fixture's own while it holds the foreground
packages/sweetview-native/test/fixtures/callback-backstop.ts	probe: drives the binding's callbacks with OS input in a process of its own (messages to its own tray, menu and single-instance windows, a WM_DROPFILES drop, the cursor over its own window, F24 and pointer moves through SendInput for the hooks), since the throw it tests must reach the binding with no Sweetview wrapper in between
packages/sweetview-native/test/fixtures/modal-loop.ts	probe: runs the application's own modal loop (MessageBoxW through its own bun:ffi table) and closes it with WM_CLOSE, to prove Sweetview's loop keeps working inside a modal loop it did not start (R1)
packages/sweetview-native/src/callbacks.test.ts	probe: delivers the OS inputs each callback kind answers (WM_COPYDATA to the single-instance window, WM_CLOSE, F24 and pointer moves through SendInput, the cursor over its own window) and reads window styles back; these are the OS's own inputs, which no Sweetview API produces
packages/sweetview-native/src/input-hooks.test.ts	probe: injects real input with SendInput (one-pixel pointer moves and the F24 key) so the system-wide hooks see it; a hook only observes input, so no Sweetview API can make any
packages/sweetview-native/src/win32/activation.test.ts	probe: hides and shows the single-instance primary's message window (FindWindowExW, SetWindowTextW) so a secondary process must retry its lookup; no Sweetview API reaches that OS state
packages/sweetview-native/src/win32/window-native.test.ts	probe: reads each window option back from the OS (title, styles, client and outer size, minimum track size, dark title bar, activation, the window under a point) and drives the resize and drag gestures with real cursor moves and a left-button press over its own window; no Sweetview API reports these OS facts
packages/sweetview-native/src/darwin/activation.test.ts	probe: macOS only: sends a secondary launch's hand-off to the primary's CFMessagePort directly, the way a second process would, to prove the native main loop receives it
packages/sweetview/src/app.test.ts	probe: on macOS replaces AppKit's button state and NSWindow's drag entry point and warps the cursor (CGWarpMouseCursorPosition) so startResize and startDrag are tested without real input; on Windows reads window styles back through packages/sweetview-native/test/win32-os.ts
packages/sweetview/test/fixtures/win-tabs.ts	probe: reads back from the OS what tabbed windows do (frame styles and metrics, hit-test edges, MINMAXINFO, the webview children's rectangles, DWM dark mode, layered alpha, a WM_DROPFILES drop, a WM_DPICHANGED sent to its own frame, screen pixels of its own frame where it is the window on top); no Sweetview API reports these OS facts
packages/sweetview/test/fixtures/win-menu-probe.ts	probe: from a second process, reads the items of the popup menu the tabs library opened and chooses or cancels one (MN_GETHMENU, MN_SELECTITEM), since nothing on the menu's own thread runs while its modal loop does
packages/sweetview/test/fixtures/win-tabs-input.ts	probe: drives the tab strip's held-button gestures (drag, resize from the top edge and corners, tab tear-off and drop) and Ctrl+T / Ctrl+W with real input (SendInput) over the fixture's own window only, and reads where its windows went and whether this thread is in the OS move loop; a gesture hands the UI thread to the OS, which only real input drives, and no Sweetview API makes input or reports these OS facts
packages/sweetview/test/fixtures/webview-file-drop.darwin.ts	probe: macOS only: calls a live WKWebView's NSDraggingDestination methods with a stand-in NSDraggingInfo whose pasteboard holds a real file URL, since a real Finder drag cannot be made from a test
demos/menubar-only/scripts/tray-drive.ts	probe: drives the demo's tray icon from a second process the way the shell and keyboard would (messages to the app's own tray-icon window and popup menu) to check the built app; it acts on another process's windows, which no Sweetview API does
demos/native-tabs/scripts/win-capture.ts	probe: captures one of this process's own windows to a PNG (PrintWindow with PW_RENDERFULLCONTENT, a DIB section) to check the native tabs demo's pixels; Sweetview has no screenshot API
demos/native-tabs/scripts/win-input.ts	probe: real mouse and keyboard input (SendInput) from a process of its own for the native tabs drive script, only while the demo's window holds the foreground, since a drag hands the app's thread to the window manager
demos/native-tabs/scripts/mac-capture.ts	probe: macOS only: captures one of this process's own windows to a PNG (CGWindowListCreateImage) to check the native tabs demo's pixels; Sweetview has no screenshot API
